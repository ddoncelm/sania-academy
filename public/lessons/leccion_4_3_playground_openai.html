Objetivo de la lección
Dominar los parámetros técnicos que controlan el comportamiento de los modelos de IA en el Playground de OpenAI y en la API — temperatura, top-p, frequency penalty, system prompts, y gestión de tokens — para obtener respuestas clínicas precisas, consistentes y dentro del presupuesto.
🎚️ Analogía clínica
Los parámetros del modelo son como los ajustes de un ventilador mecánico: el médico novato lo deja en modo automático y funciona razonablemente. El intensivista experimentado ajusta la presión soporte, el PEEP, la FiO₂ y la frecuencia respiratoria para el paciente concreto, obteniendo un resultado óptimo que el modo automático no alcanza. La temperatura del modelo es el PEEP de la IA clínica — si no la ajustas, el modelo funciona, pero no al nivel que necesitas para documentación clínica de precisión.
Por qué los parámetros importan en clínica
Un modelo con temperatura 0.9 que genera respuestas creativas y variadas es perfecto para brainstorming de estrategias de innovación. El mismo modelo con temperatura 0.9 generando diagnósticos diferenciales puede incluir diagnósticos improbables o inconsistentes entre ejecuciones. Para uso clínico, la calibración de parámetros no es opcional — es parte del control de calidad del sistema.
Temperatura y top-p: los parámetros de creatividad vs. precisión
🌡️ Temperatura
Rango: 0.0 — 2.0 · Valor por defecto: 1.0 · Recomendado clínica: 0.1 — 0.4
Controla la aleatoriedad de las respuestas. Temperatura baja = el modelo elige siempre la palabra más probable → respuestas predecibles, consistentes, conservadoras. Temperatura alta = el modelo considera palabras menos probables → respuestas más variadas, creativas, a veces incoherentes.

En clínica: la consistencia entre ejecuciones es crítica. Si el mismo caso clínico con los mismos datos produce diagnósticos distintos cada vez, el profesional no puede confiar en el sistema. Temperatura baja garantiza consistencia.
0.0
Determinista
Siempre la misma respuesta exacta. Documentación clínica estandarizada.
0.3
Preciso
Ligera variación. Ideal para diagnóstico diferencial y análisis clínico.
0.7
Equilibrado
Balance creatividad/precisión. Educación sanitaria, comunicación al paciente.
TEMPERATURA ÓPTIMA POR CASO DE USO CLÍNICO: Temperatura 0.0 — 0.2 (máxima consistencia): → Informes de alta con formato estandarizado → Aplicación de escalas clínicas (Braden, Barthel, NIHSS) → Cálculo de dosis y ajustes farmacológicos → Conciliación de medicación → Verificación de criterios diagnósticos (cumple/no cumple) Temperatura 0.2 — 0.4 (alta precisión con algo de variabilidad): → Diagnóstico diferencial ordenado por probabilidad → Resumen de historia clínica → Análisis de pruebas complementarias → Recomendaciones de tratamiento basadas en guías Temperatura 0.4 — 0.6 (equilibrio): → Educación al paciente (misma información, distintas formulaciones) → Interpretación de resultados para un paciente concreto → Cartas de derivación personalizadas Temperatura 0.6 — 0.9 (creatividad moderada): → Brainstorming de posibles mejoras del servicio → Redacción de materiales de comunicación variados → Generación de casos clínicos ficticios para formación Temperatura >0.9: NO recomendado para ningún uso clínico
🎯 Top-p (Nucleus sampling)
Rango: 0.0 — 1.0 · Valor por defecto: 1.0 · Recomendado clínica: 0.85 — 0.95
Alternativa a la temperatura para controlar la variabilidad. En lugar de escalar todas las probabilidades (temperatura), top-p recorta el vocabulario a las palabras que suman el p% de probabilidad acumulada. Con top-p = 0.9, el modelo solo considera las palabras que suman el 90% de probabilidad total — las más improbables quedan excluidas.

En la práctica: temperatura y top-p controlan lo mismo desde perspectivas distintas. La recomendación de OpenAI es ajustar uno y dejar el otro en su valor por defecto. Para clínica, preferir temperatura baja (0.2-0.4) + top-p en 1.0.
0.85
Conservador
Solo palabras de alta probabilidad. Muy consistente, puede ser repetitivo.
0.95
Recomendado
Equilibrio para uso clínico. Excluye salidas improbables sin sacrificar fluidez.
1.0
Sin filtro
Default. Todas las palabras posibles. Combinar con temperatura baja.
🔁 Frequency Penalty y Presence Penalty
Rango: -2.0 — 2.0 · Valor por defecto: 0.0
Frequency Penalty: penaliza la repetición de palabras que ya han aparecido mucho en la respuesta. Útil para evitar que el modelo repita el mismo diagnóstico o la misma frase de múltiples formas. Para clínica: 0.2-0.5 reduce la verbosidad sin sacrificar exactitud.

Presence Penalty: penaliza cualquier palabra que ya haya aparecido (no por frecuencia sino por presencia). Fuerza al modelo a introducir más vocabulario nuevo. Para clínica: 0.0-0.3. Valores altos pueden hacer que el modelo evite repetir términos médicos necesarios.
⚠️ Error frecuente: ajustar frequency penalty demasiado alto
Con frequency penalty alto (>0.8), el modelo puede evitar repetir el nombre del medicamento o el diagnóstico — precisamente los términos que más necesitan repetirse para claridad clínica. Para documentación médica, mantener frequency penalty entre 0.2 y 0.5 máximo.
System prompts médicos: la configuración más importante
El system prompt es la instrucción que el modelo recibe antes de cualquier conversación con el usuario. Es el equivalente al briefing que le das a un profesional antes de que empiece a trabajar. En clínica, un system prompt bien diseñado puede ser la diferencia entre un modelo que genera texto médico genérico y uno que produce documentación de calidad para tu servicio específico.
Los 6 componentes de un system prompt clínico efectivo
1️⃣
Identidad y rol
Define quién es el modelo: «Eres el asistente clínico del Servicio de Cardiología del Hospital X, especializado en insuficiencia cardíaca y cardiopatía isquémica». Cuanto más específico, mejor — el modelo activa el conocimiento relevante para ese rol.
2️⃣
Contexto de uso
Describe el entorno: «Este asistente es usado exclusivamente por cardiólogos y residentes de cardiología para apoyo a la documentación clínica». Establece las expectativas de nivel técnico y el contexto de las respuestas.
3️⃣
Reglas de comportamiento
Las reglas no negociables: «Nunca inventes datos clínicos no proporcionados. Si un campo está vacío, indícalo explícitamente como "pendiente de completar". Si no estás seguro de algo, di que no tienes esa información». Las reglas de comportamiento son el control de seguridad del sistema.
4️⃣
Formato de respuesta
Define exactamente el formato: «Los informes de alta deben tener estas secciones en este orden: [lista]. Los diagnósticos secundarios se listan usando CIE-10. Las dosis se expresan en mg/kg para pacientes pediátricos y en mg absolutos para adultos».
5️⃣
Restricciones de dominio
Lo que el modelo NO debe hacer: «No hagas recomendaciones de medicación de alto riesgo sin que el médico las valide explícitamente. No generes información sobre prescripción de opioides sin un aviso visible. No respondas preguntas fuera del ámbito de la cardiología».
6️⃣
Aviso de responsabilidad integrado
Inclúyelo en el system prompt y pídele al modelo que lo repita en las respuestas relevantes: «Cuando generes diagnósticos o recomendaciones terapéuticas, añade al final: "Este análisis es un apoyo clínico. La responsabilidad diagnóstica y terapéutica es del médico responsable del paciente"».

Trabajas exclusivamente con médicos internistas y médicos de guardia de este servicio. Cómo testear un system prompt antes de desplegarlo
PROTOCOLO DE TESTING DE SYSTEM PROMPT: PASO 1 — CASOS ESTÁNDAR (happy path): → Testear con 5 casos clínicos representativos del servicio → Verificar: formato correcto, terminología adecuada, información completa → Verificar: el aviso de responsabilidad aparece donde corresponde PASO 2 — CASOS LÍMITE: → ¿Qué pasa si el usuario pregunta algo fuera del dominio? (política del hospital, temas no clínicos, recetas para casa) → El modelo debe rechazar o redirigir → ¿Qué pasa con información clínica ambigua o incompleta? → ¿Qué pasa si el usuario pide algo que viola las restricciones definidas? PASO 3 — CASOS DE SEGURIDAD: → ¿El modelo inventa datos cuando no se los proporcionan? → ¿Añade el aviso de validación en los análisis diagnósticos? → ¿Marca correctamente los medicamentos de estrecho margen terapéutico? PASO 4 — CONSISTENCIA: → Ejecutar el mismo caso clínico 5 veces (con temperatura 0.3) → Las respuestas deben ser clínicamente equivalentes aunque no idénticas PASO 5 — VALIDACIÓN CON USUARIOS REALES: → 2-3 médicos del servicio prueban con sus propios casos → Recoger feedback: ¿el formato es útil? ¿falta algo? ¿sobra algo? → Iterar el system prompt según el feedback antes de despliegue

Gestión de tokens y optimización de costes
Los modelos de IA de la API se cobran por token — unidades de texto de aproximadamente 0.75 palabras. Para uso clínico intensivo, la gestión de tokens es fundamental tanto para controlar el coste como para no superar los límites de la ventana de contexto.
TOKENS EN PRÁCTICA CLÍNICA: Aproximación útil: 1 token ≈ 0.75 palabras en inglés 1 token ≈ 0.6 palabras en español (más tokens por palabra) Ejemplo — Informe de alta estándar: → System prompt: ~500 tokens → Input (datos del caso): ~800 tokens → Output (informe generado): ~600 tokens → Total por informe: ~1.900 tokens Con GPT-4o (precios aproximados 2024): → Input: $2.50 / 1M tokens → 1.300 tokens de input ≈ $0.003 → Output: $10.00 / 1M tokens → 600 tokens de output ≈ $0.006 → Coste por informe: ~$0.009 (menos de 1 céntimo) Escala: 100 informes/mes = ~$0.90/mes 1.000 informes/mes = ~$9/mes GPT-4o-mini (10x más barato, calidad suficiente para documentación estructurada): → 1.000 informes/mes ≈ $0.90/mes Conclusión: el coste de tokens raramente es el factor limitante para uso clínico razonable. La ventana de contexto sí puede serlo.
📏
Ventana de contexto: el límite real
La ventana de contexto es el máximo de tokens que el modelo puede procesar en una sola llamada (input + output). GPT-4o: 128.000 tokens. Claude 3.5 Sonnet: 200.000 tokens. Un informe de 2.000 tokens + system prompt de 500 tokens + 5 documentos RAG de 3.000 tokens cada uno = 17.500 tokens. Bien dentro del límite. El problema ocurre cuando el sistema RAG incluye demasiados documentos o el historial de conversación es muy largo.
💡
Estrategias para controlar el tamaño del contexto
En RAG: limitar a 3-5 fragmentos de documentos por consulta (no todos los documentos de la base). En conversaciones largas: resumir el historial en lugar de incluirlo completo. En system prompts: no incluir ejemplos extensos de casos clínicos — usar instrucciones concisas. Usar modelos más pequeños (GPT-4o-mini, Claude Haiku) para tareas donde la calidad no es crítica.
