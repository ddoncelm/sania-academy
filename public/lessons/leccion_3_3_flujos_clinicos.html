Objetivo de la lección
Dominar la metodología completa para diseñar, construir, probar y desplegar flujos de automatización clínica — desde la identificación del proceso hasta la validación en producción. Al finalizar, sabrás transformar cualquier proceso repetitivo sanitario en un flujo funcional.
🏗️ Analogía clínica
Diseñar un flujo de automatización es como elaborar un protocolo clínico: no empiezas escribiendo los pasos sin antes revisar la evidencia y el proceso actual. Primero mapeas lo que ya se hace (proceso as-is), identificas las ineficiencias, defines el proceso mejorado (to-be), y solo entonces lo implementas y validas. El flujo automático es el protocolo ejecutable — si el protocolo tiene errores, la automatización los ejecutará a velocidad de máquina.
Las 6 fases de la metodología
No saltes pasos. En sanidad cada fase tiene su justificación clínica y técnica.
1
Identificar y acotar el proceso
Define exactamente qué proceso automatizas: dónde empieza, dónde termina, quién lo ejecuta actualmente y cuántas veces por semana. Un proceso mal acotado genera un flujo que automatiza solo la mitad del problema.
2
Mapear el proceso actual (as-is)
Entrevista a quien ejecuta el proceso hoy. Documenta cada paso real — incluyendo las excepciones que no están en el protocolo oficial. Los pasos informales (el «ya sé yo que cuando pasa X hay que hacer Y») son los que hacen fallar la automatización.
3
Diseñar el proceso mejorado (to-be)
Elimina pasos que no añaden valor antes de automatizar. Define el proceso ideal con el equipo implicado. Este es el proceso que automatizarás — no el actual, sino el mejorado. Documenta las reglas de negocio con lógica explícita: «Si A → entonces B; si no → entonces C».
4
Construir el flujo en la plataforma
Implementa el flujo diseñado en Zapier, Make o n8n. Empieza con el happy path (el caso estándar sin excepciones), luego añade el manejo de excepciones. Documenta cada nodo con comentarios que expliquen por qué hace lo que hace.
5
Testing exhaustivo antes de producción
Prueba el flujo con datos reales anonimizados en entorno de pruebas. Testea el happy path, todos los casos de excepción identificados, y los casos límite (campos vacíos, caracteres especiales en nombres, teléfonos incorrectos). Valida con los usuarios finales antes del despliegue.
6
Despliegue progresivo y monitorización
Activa el flujo primero para un subconjunto (un servicio, una semana, 100 registros). Monitoriza los primeros resultados. Si hay problemas: desactiva, corrige, reactiva. Nunca despliegues directamente al 100% sin validación parcial previa.
Los componentes de cualquier flujo de automatización
Todo flujo, por complejo que sea, está construido con estos bloques. Dominarlos te permite diseñar cualquier automatización sanitaria.
Triggers — El disparador del flujo
El trigger define QUÉ hace que el flujo empiece. Es el evento que desencadena toda la automatización. Elegir el trigger correcto es la decisión más importante del diseño.
⏰
Trigger por tiempo (Schedule)
Se activa a una hora/frecuencia programada. Ej: «Cada lunes a las 7:00», «Cada 6 horas», «Primer día del mes». Ideal para: reporting periódico, recordatorios a fecha futura calculada, comprobaciones de stock diarias. Limitación: no reacciona a eventos en tiempo real.
📋
Trigger por nuevo dato (New Record)
Se activa cuando aparece un nuevo elemento en una fuente de datos: nueva fila en Google Sheets, nuevo registro en Airtable, nuevo correo en una bandeja específica, nuevo formulario enviado. El más usado en flujos de citación y admisión.
🔔
Trigger por Webhook (evento en tiempo real)
El sistema externo (HIS, laboratorio, formulario web) envía una señal a la plataforma de automatización en el momento en que ocurre el evento. Es el trigger más rápido y potente. Requiere que el sistema origen soporte webhooks. Ideal para: alertas de valores críticos, notificaciones de alta, triaje en tiempo real.
✏️
Trigger por modificación de datos (Updated Record)
Se activa cuando un registro existente cambia. Ej: cuando el campo «Estado» en la hoja de citas cambia de «Pendiente» a «Cancelada». Permite reaccionar a cambios de estado del paciente, resultados de pruebas actualizados, o cambios en la agenda.

Acciones — Lo que hace el flujo
Las acciones son las operaciones que el flujo ejecuta una vez disparado. Pueden encadenarse en secuencia o ejecutarse en paralelo. Cada acción trabaja sobre los datos del trigger o los generados por acciones anteriores.
📤
Enviar mensaje (SMS, email, WhatsApp, push)
La acción más común en sanidad. Permite personalizar el mensaje con datos del trigger (nombre del paciente, fecha de cita, servicio). Servicios: Twilio (SMS), Gmail/Outlook (email), WhatsApp Business API, notificaciones de apps móviles.
💾
Crear o actualizar registro
Añadir una fila a Google Sheets, crear una tarea en Asana, actualizar el estado en Airtable, insertar en una base de datos SQL. Fundamental para construir el registro de trazabilidad de cada ejecución del flujo.
📄
Generar documento
Crear un PDF, un documento Word o un informe a partir de una plantilla rellena con los datos del flujo. Ej: informe de alta personalizado, carta de derivación, notificación formal de resultado. Herramientas: Google Docs (con plantillas), Carbone, html-pdf.
🌐
Llamada HTTP / API Request
Envía una petición a cualquier sistema con API REST: el HIS, el sistema de laboratorio, el sistema de farmacia, un servicio externo de validación. Es la acción más potente — permite conectar la automatización con prácticamente cualquier sistema hospitalario que tenga API.
Filtros y condiciones — La inteligencia del flujo
Los filtros hacen que el flujo tome decisiones: continúa solo si se cumple una condición, o bifurca hacia caminos diferentes según el valor de un campo. Son la diferencia entre un flujo simple y un flujo inteligente.
🔀
Router / Switch — bifurcación múltiple
Divide el flujo en ramas según el valor de un campo. Ej: si Tipo_Consulta = «Primera» → enviar documentación preprocedimiento; si = «Revisión» → enviar solo recordatorio; si = «Urgente» → notificar también al médico. Cada rama puede tener acciones completamente distintas.
⛔
Filtro de continuación — stop si no cumple
Detiene el flujo si no se cumple una condición. Ej: «Continúa solo si el campo Teléfono no está vacío». Evita que el flujo falle o envíe mensajes sin destinatario cuando hay datos incompletos. Esencial para flujos robustos.
🔁
Iterator / For-each — procesar listas
Cuando el trigger devuelve una lista (ej: todos los pacientes con cita mañana), el iterator procesa cada elemento de la lista de forma independiente, ejecutando las acciones para cada uno. Fundamental para flujos de notificación masiva o reporting que agregan múltiples registros.
⏳
Delay — retraso programado
Pausa el flujo un tiempo definido antes de continuar. Ej: trigger cuando se registra la cita → delay de 5 días → enviar recordatorio (que llega 2 días antes de la cita de 7 días). Permite construir secuencias de comunicación escalonadas en el tiempo.
Manejo de errores — Flujos que fallan con gracia
En sanidad, un flujo que falla silenciosamente puede ser más peligroso que no tener automatización. El manejo de errores define qué hace el flujo cuando algo sale mal, asegurando que los fallos sean visibles y recuperables.
📬
Notificación de error al responsable
Cuando cualquier paso del flujo falla, el sistema envía automáticamente un email/SMS al administrador del flujo con el detalle del error: qué paso falló, qué datos tenía en ese momento, y el mensaje de error técnico. Sin esto, los fallos pasan inadvertidos.
🔄
Reintentos automáticos
Si un paso falla por un error transitorio (la API del HIS no respondió en ese momento), la plataforma lo reintenta automáticamente N veces con un intervalo creciente (1 min, 5 min, 30 min). Si tras N reintentos sigue fallando, entonces notifica al administrador. Make y n8n tienen reintentos configurables.
📝
Registro de errores (error log)
Mantén un registro de todos los fallos: timestamp, qué registro estaba procesando, qué error ocurrió, si se resolvió o no. Este log es tu herramienta de diagnóstico cuando alguien dice «el sistema no envió mi recordatorio». Con el log puedes verificarlo en segundos.
🚫 Error crítico: flujos silenciosos que fallan
Un flujo de notificación de valores críticos que falla sin avisar puede tener consecuencias clínicas graves. Cualquier flujo de criticidad asistencial debe tener: (1) notificación de error en tiempo real, (2) reintentos automáticos, (3) escalado a supervisión humana si el fallo persiste. La automatización no debe crear un punto único de fallo invisible.

Si no → STOP (cita muy próxima, va al flujo urgente) PASO 2 — Calcular fecha del recordatorio → Fecha recordatorio 1 = Fecha_Cita - 7 días → Fecha recordatorio 2 = Fecha_Cita - 2 días PASO 3 — Delay hasta recordatorio 1 → Make: módulo "Sleep" hasta Fecha_recordatorio_1 a las 10:00 PASO 4 — SMS recordatorio 1 (Twilio) → Mensaje: "Hola {{Nombre}}, le recordamos su cita en {{Servicio}} el {{Fecha_Cita}} en el [Hospital]. Responda SI para confirmar o NO para cancelar. Tel. [contacto]" PASO 5 — Watch SMS response (Twilio webhook, 48h de espera) → Router según respuesta: → "SI" / "S" / "Sí": actualizar Estado → "Confirmada_paciente" + log → "NO" / "N": actualizar Estado → "Cancelada_paciente" + notificar admisiones → Sin respuesta en 48h: continuar al Paso 6 PASO 6 — Delay hasta recordatorio 2 (T-48h) → SMS recordatorio 2: confirmación + instrucciones específicas del servicio PASO 7 — Registro de trazabilidad → Actualizar hoja "Log_Recordatorios": Nombre, Fecha, SMS1_enviado, SMS2_enviado, Respuesta MANEJO DE ERRORES: → Si Twilio falla: reintentar 2 veces (intervalo 10 min) → Si reintento falla: email a administracion@hospital.es con detalle del fallo

Testing y validación antes de producción
El testing en automatización sanitaria no es opcional — es una obligación clínica. Un flujo con errores puede no enviar alertas críticas, enviar mensajes incorrectos a pacientes, o corromper datos de calidad. Esta checklist garantiza que el flujo está listo para producción.
✅ Analogía clínica
El testing de un flujo de automatización equivale a la simulación en el quirófano antes de una cirugía nueva: ensayas el procedimiento con condiciones controladas, identificas los fallos posibles, los corriges, y solo entonces operas al paciente real. Ningún cirujano estrena una técnica directamente en quirófano — ningún flujo va a producción sin testing exhaustivo.
Checklist de validación pre-producción
Marca cada elemento antes de activar el flujo en producción:
Happy path: El flujo completo se ejecuta correctamente con datos estándar de prueba desde el inicio hasta el final
Campos vacíos: El flujo maneja correctamente los registros con campos obligatorios vacíos (no falla, registra el error y notifica)
Datos malformados: Teléfonos con formato incorrecto, fechas inválidas, caracteres especiales en nombres no rompen el flujo
Condiciones límite: Los casos en el borde de las condiciones (exactamente en el umbral) se comportan correctamente
Manejo de errores: Simular fallo de un paso (desactivar temporalmente un servicio) y verificar que el error se notifica correctamente
Reintentos: Verificar que los reintentos funcionan y que el flujo no duplica acciones al reintentar
Validación con usuario final: La persona que actualmente ejecuta el proceso manualmente ha revisado y aprobado el flujo automatizado
Trazabilidad: Cada ejecución queda registrada con suficiente detalle para auditoría (timestamp, datos procesados, resultado)
RGPD: DPA firmado con el proveedor (si aplica), minimización de datos verificada, retención de logs configurada
Plan de rollback: Documentado el procedimiento para desactivar el flujo y volver al proceso manual si hay problemas en producción
