Objetivo de la leccion
Entender como conectar dispositivos de monitorizacion clinica (wearables, sensores IoT, glucometros, oximetros, tensiometros inteligentes) con sistemas de IA que procesan senales biometricas en tiempo real y generan alertas que permiten intervenir antes de que el paciente llegue a urgencias.
Analogia clinica
El IoT clinico es la extension del monitor del paciente hasta su domicilio. En UCI, monitorizar 10 parametros continuamente salva vidas. El IoT clinico lleva esa logica al cronica en casa: la tension de la manana, el peso diario, la saturacion nocturna. La IA procesa esas senales y detecta el patron de deterioro 5 dias antes de que llegue a urgencias. No es ciencia ficcion — es lo que los mejores programas de telemonitorizacion ya hacen con tecnologia disponible hoy.
⌚
Wearables de consumo
Apple Watch, Garmin, Fitbit. FC, SpO2, actividad. APIs disponibles. No certificados CE como dispositivo medico pero utiles para tendencias en programas informales.
🏥
Dispositivos medicos certificados
Withings, Nonin, Beurer. Certificacion CE como dispositivo medico. APIs documentadas. Datos clinicamente validados. Los adecuados para programas hospitalarios formales.
💉
Monitorizacion continua
Dexcom G7 (MCG), AliveCor Kardia (ECG). Flujo continuo de datos. El nivel mas avanzado de telemonitorizacion domiciliaria actualmente disponible.
🔐
Datos de salud bajo RGPD
Los datos biometricos de wearables son datos de salud de categoria especial (Art. 9 RGPD) cuando se asocian a persona identificable. Requieren DPA, base legal y consentimiento especifico.
APIs y protocolos de integracion
Tres vias para recibir datos de dispositivos IoT en el sistema clinico, ordenadas de mas a menos latencia.
API REST — el protocolo mas accesible
El sistema clinico llama periodicamente a la API del fabricante para obtener los datos mas recientes. Latencia maxima = intervalo de polling. Mas facil de implementar en Make o n8n.
EJEMPLO — API Withings (tensiometro + bascula certificados CE): GET https://wbsapi.withings.net/measure?action=getmeas&meastypes=1,9,10 → meastypes: 1=peso (kg), 9=TA diastolica, 10=TA sistolica → Autenticacion: OAuth 2.0 (el paciente autoriza el acceso) → Devuelve: [{timestamp, value, type, unit}] EJEMPLO — API Dexcom (MCG glucosa): GET https://api.dexcom.com/v2/users/self/egvs?startDate=X&endDate=Y → Devuelve: glucosa intersticial cada 5 min + tendencia → trend: "DoubleUp" | "SingleUp" | "Flat" | "SingleDown" | "DoubleDown" → trendRate: mg/dL por minuto (positivo = subiendo) EN MAKE: → Schedule cada 15-30 min → HTTP Request a API → procesar respuesta → Latencia maxima: 15-30 minutos (suficiente para seguimiento diario) → NO suficiente para alertas urgentes (usar MQTT en esos casos)

MQTT — Push en tiempo real para alertas criticas
El dispositivo publica datos en un broker MQTT en el momento de la medicion. El sistema clinico esta suscrito y los recibe en segundos. Latencia: 2-10 segundos. Ideal para SpO2, FC, glucosa.
ARQUITECTURA MQTT: DISPOSITIVO (oximetro Nonin) → publica en broker: Topic: "paciente/12345/spo2" Payload: {"ts":"2025-01-15T09:32:00Z","spo2":94,"hr":87} Frecuencia: cada 5 minutos BROKER MQTT (en servidor del hospital): Mosquitto (open source) / HiveMQ (enterprise) Gestiona autenticacion y enrutamiento n8n SELF-HOSTED (suscrito al broker): Trigger: "MQTT message received" Topic: "paciente/+/spo2" (wildcard + = cualquier paciente) Accion: extraer patient_id → comparar con umbral personalizado Si SpO2 menor que umbral: activar alerta en segundos DIFERENCIA CLAVE vs. API REST: API REST polling 15min: si la desaturacion ocurre a las 09:00, el sistema no sabe hasta las 09:15 (en el peor caso). MQTT: sabe a las 09:00:05. En una desaturacion severa, esos 15 minutos pueden ser clinicamente relevantes.
FHIR Observation — Estandar sanitario para datos de dispositivos
Los datos de dispositivos IoT pueden enviarse directamente al HIS como recursos FHIR Observation, integrando la telemonitorizacion en la historia clinica electronica sin sistemas intermediarios propietarios.
FHIR Observation para SpO2 de oximetro domiciliario: { "resourceType": "Observation", "status": "final", "code": {"coding": [{"system":"http://loinc.org", "code":"59408-5", "display":"Oxygen saturation"}]}, "subject": {"reference": "Patient/12345"}, "device": {"reference": "Device/nonin-3230-serial123"}, "effectiveDateTime": "2025-01-15T09:32:00Z", "valueQuantity": {"value": 94, "unit": "%"}, "interpretation": [{"coding": [{"code": "L", "display": "Low"}]}] } Codigos LOINC utiles: 59408-5 = SpO2 55284-4 = TA (sistolica + diastolica) 8302-2 = Talla 29463-7 = Peso 2339-0 = Glucosa en sangre 8867-4 = Frecuencia cardiaca
Dispositivos clave por patologia y umbrales personalizados
⚖️
Bascula conectada — el dispositivo mas impactante en IC
Withings Body Scan (CE clase IIa) o Beurer BF700. Pesaje diario en ayunas. Umbral de alerta estandar: +2 kg en 24h o +3.5 kg en 7 dias respecto al peso basal del paciente. Evidencia publicada: reduccion de reingresos por IC del 30-45% en programas con telemonitorizacion de peso. El medico define el umbral personalizado para cada paciente al inscribirlo en el programa.
💓
Tensiometro y pulsioximetro conectados
Withings BPM Connect (validado clinicamente). Umbrales tipicos: TAS mayor de 180 o menor de 90 / FC mayor de 120 o menor de 50 en dos mediciones consecutivas. Los umbrales deben personalizarse segun el tratamiento de base del paciente (ej: un paciente en beta-bloqueante puede tener FC habitual de 55 lpm — el umbral bajo de 50 seria correcto, no 60).
🩸
Oximetro de pulso — fundamental en EPOC y fibrosis
Nonin 3230 (certificacion FDA/CE dispositivo medico). Umbral de alerta estandar: SpO2 menor del 92% en dos mediciones o menor del 90% en una sola. Para EPOC grave: el umbral DEBE individualizarse — pacientes con SpO2 basal del 88-90% necesitan umbrales distintos. Sin individualizacion, el sistema genera alertas permanentes en pacientes estables o suprime alertas reales.
🌬️
Telespirometro domiciliario
Nuvoair (CE, telespirometria validada). Mide FEV1 y FVC. Umbral de alerta: caida del FEV1 mayor del 20% respecto al mejor valor personal = senal de exacerbacion incipiente. Permite intervenir con tratamiento oral antes de que la exacerbacion requiera ingreso hospitalario.
💉
Monitor Continuo de Glucosa (MCG)
Abbott FreeStyle Libre 3 o Dexcom G7. Dato de glucosa intersticial cada 5 minutos. Umbrales: hipoglucemia menor de 70 mg/dL / hiperglucemia mayor de 250 mg/dL. La tendencia (DoubleDown = bajando 2 mg/dL/min) es tan importante como el valor: glucemia de 100 con DoubleDown puede llegar a hipoglucemia en 15 minutos — alerta preventiva antes de que cruce el umbral.
LOGICA DE ALERTA CON TENDENCIA (MCG): valor_actual = 100 mg/dL ← en rango normal trendRate = -2.0 mg/dL/min ← DoubleDown tiempo_hasta_hipoglucemia = (100 - 70) / 2 = 15 minutos if tiempo_hasta_hipoglucemia < 20: ALERTA PREVENTIVA → "Su glucemia esta bajando rapidamente. Considere tomar carbohidratos de absorcion rapida." Esto es lo que diferencia el MCG de la glucemia capilar: no mide el valor actual sino la trayectoria → capacidad predictiva.
Alertas inteligentes: mas alla del umbral simple
Los sistemas de alerta simples (si X mayor que umbral → alerta) generan demasiados falsos positivos. La IA permite alertas contextuales que consideran la tendencia, el patron temporal y el historial del paciente.
📊
Tendencia vs. valor puntual
Un paciente con IC que pesa 75.2 kg hoy: si ayer pesaba 75.0 kg → sin alerta. Si hace 4 dias pesaba 73.5 kg y lleva subiendo 0.4 kg/dia → alerta de acumulacion progresiva aunque ningun valor individual haya cruzado el umbral de +2 kg en 24h. La IA analiza la serie temporal completa.
🔗
Correlacion entre multiples senales
+2 kg de peso solo puede ser IC o simplemente haber comido mucho. Combinar con FC elevada + SpO2 bajando + cuestionario PRO con mas disnea → el patron combinado apunta a descompensacion incipiente con alta probabilidad. La correlacion reduce los falsos positivos del umbral simple.

VARIACION NORMAL: cambios dentro de la variabilidad esperada para este paciente 4. Convierte datos brutos de IoT en analisis clinico accionable en 30 segundos. El medico se enfoca en los pacientes con patron preocupante en lugar de revisar todos los datos de todos los pacientes cada dia — exactamente el beneficio esperado de la telemonitorizacion basada en IA.
