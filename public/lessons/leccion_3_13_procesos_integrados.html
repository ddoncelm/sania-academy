Orquestación de automatizaciones complejas:
dependencias, sincronización y monitorización del ecosistema
15-20 minutos
Nivel avanzado
Arquitectura de automatización
0%
Objetivo de la lección
Pasar de gestionar flujos individuales a orquestar un ecosistema de automatizaciones que trabajan coordinadas: gestionar las dependencias entre flujos, sincronizar datos compartidos, detectar y recuperarse de fallos del sistema, y mantener el ecosistema actualizado y funcionando a lo largo del tiempo.
🏥 Analogía clínica
Un único flujo de automatización es como un protocolo clínico aislado — valioso por sí mismo pero limitado. Un ecosistema de automatizaciones orquestadas es como el sistema de guardia de un hospital: múltiples equipos (urgencias, quirófano, UCI, laboratorio) que trabajan de forma autónoma pero coordinada, con protocolos de comunicación entre ellos, un sistema de información que los conecta, y un coordinador de guardia que gestiona cuando hay conflictos o fallos. La orquestación es exactamente ese coordinador.
Del flujo aislado al ecosistema integrado
Después de implementar los flujos de las lecciones anteriores, el hospital tiene decenas de automatizaciones activas. Sin orquestación, surgen tres problemas:
⚠️
Conflictos de datos
El flujo de recordatorios usa Google Sheets como fuente de verdad para las citas. El flujo de gestión de listas de espera también escribe en esa hoja. El flujo de reporting lee de ella. Si dos flujos escriben simultáneamente sin coordinación, los datos se corrompen. Se necesita gestión de concurrencia.
⚠️
Dependencias ocultas
El flujo de encuestas post-alta depende de que el flujo de altas lo haya procesado primero. El flujo de dashboard depende de que los flujos de calidad hayan actualizado los datos a las 7:00 AM. Si un flujo falla, los que dependen de él también fallan — silenciosamente si no hay monitorización.
⚠️
Imposibilidad de mantener sin documentación
Seis meses después de implementar 20 flujos, nadie recuerda exactamente qué hace cada uno, qué datos usa, de dónde los toma, qué servicios externos necesita, y qué pasa si alguno falla. La documentación y la monitorización son la única forma de que el ecosistema sea mantenible a largo plazo.
Gestión de dependencias entre flujos
Una dependencia es cuando un flujo B necesita que el flujo A haya completado correctamente antes de poder ejecutarse. Identificar, documentar y gestionar estas dependencias es la base de un ecosistema estable.
Cómo documentar el mapa de dependencias del ecosistema
INVENTARIO DE FLUJOS — plantilla de documentación: Para cada flujo en el ecosistema, registrar: ┌─────────────────────────────────────────────────────┐ │ FLUJO: [nombre descriptivo] │ │ ID: [código único, ej: F-003] │ │ Plataforma: Make / n8n / Zapier │ │ Trigger: [tipo y fuente] │ │ Frecuencia: [schedule o event-driven] │ │ │ │ ENTRADAS (fuentes de datos que consume): │ │ - [fuente 1]: [tipo de dato, con qué frecuencia] │ │ - [fuente 2]: ... │ │ │ │ SALIDAS (datos que produce o sistemas que modifica):│ │ - [destino 1]: [qué escribe/actualiza] │ │ - [destino 2]: ... │ │ │ │ DEPENDENCIAS: │ │ - Depende de: [F-001, F-002] (no puede ejecutarse │ │ si estos fallan) │ │ - Bloqueado por: [F-005] (no deben ejecutarse a la │ │ vez porque escriben en la misma fuente) │ │ │ │ SERVICIOS EXTERNOS: │ │ - [servicio 1]: [qué usa, endpoint, credenciales] │ │ │ │ QUÉ PASA SI FALLA: │ │ - Impacto: [describe el impacto clínico/operativo] │ │ - Tiempo máximo de inactividad tolerable: [horas] │ │ - Procedimiento manual de respaldo: [descripción] │ └─────────────────────────────────────────────────────┘
Prompt: auditar y documentar el ecosistema de automatizaciones del servicio
Soy responsable del ecosistema de automatizaciones del Servicio de [ESPECIALIDAD]. Tenemos los siguientes flujos activos: [LISTA DE FLUJOS: nombre, plataforma, frecuencia, descripción breve de qué hace] Para cada flujo, necesito que me ayudes a: 1. Identificar las dependencias con otros flujos del ecosistema (¿cuál necesita que otro esté funcionando?) 2. Identificar las dependencias con servicios externos (¿qué APIs, plataformas de terceros usa?) 3. Detectar posibles conflictos de escritura (¿dos flujos modifican la misma fuente de datos?) 4. Ordenar los flujos por criticidad: ¿cuáles tienen impacto clínico directo si fallan? 5. Para los flujos más críticos: ¿cuál sería el procedimiento manual de respaldo si la automatización falla? Genera: - El mapa de dependencias en formato visual (árbol o lista anidada) - La clasificación por criticidad (crítico / importante / auxiliar) - Los 3 puntos de fallo único más peligrosos del ecosistema actual - Recomendaciones para reducir esos puntos de fallo
Un ecosistema de automatizaciones sin documentación es una deuda técnica que crece silenciosamente. Esta auditoría, hecha periódicamente (trimestral o tras cada cambio significativo), mantiene el control de lo que existe, cómo interactúa, y qué pasa cuando algo falla.
Sincronización: evitar conflictos de escritura concurrente
Cuando dos flujos leen y escriben en la misma fuente de datos (Google Sheets, Airtable, base de datos), pueden producirse condiciones de carrera — ambos leen el valor antiguo, ambos calculan en paralelo, ambos escriben — y el resultado final es incorrecto.
⏰
Solución 1: separación temporal
Si dos flujos deben escribir en la misma fuente, programarlos en horarios que no se solapen. El flujo de reporting que actualiza el dashboard ejecuta a las 7:00 AM; el flujo de calidad que alimenta los datos ejecuta a las 6:30 AM. 30 minutos de separación garantiza que uno termina antes de que el otro empiece.
🔒
Solución 2: flag de «en proceso»
El flujo que empieza a escribir marca una celda/campo como «PROCESANDO» al inicio. El segundo flujo, antes de escribir, comprueba ese flag. Si está en «PROCESANDO», espera o se re-agenda. Al terminar el primero, marca como «LIBRE». Implementable con una celda adicional en Sheets o un campo en Airtable.
📋
Solución 3: datos solo de lectura para flujos secundarios
Designar una fuente de datos como «fuente de verdad» que solo un flujo principal escribe. Los flujos secundarios solo leen de ella — nunca escriben. Los flujos secundarios escriben en sus propias hojas/tablas si necesitan registrar algo. Elimina el problema de raíz para la mayoría de los casos.
Circuit breaker: desconectar automáticamente flujos cuando el sistema está inestable
El patrón «circuit breaker» (disyuntor automático) es un mecanismo que desactiva temporalmente un flujo cuando detecta que está fallando repetidamente — antes de que el fallo en cascada afecte a todo el ecosistema.
IMPLEMENTACIÓN DE CIRCUIT BREAKER EN MAKE: ESTADO INICIAL: Cerrado (flujo funcionando normal) MONITORIZACIÓN: contador de fallos consecutivos en campo de Sheets Si el flujo falla en una ejecución: → Incrementar contador_fallos + 1 → Si contador_fallos < 3: reintentar (reintentos normales de Make) → Si contador_fallos >= 3 (umbral): → ABRIR el circuito: desactivar el escenario en Make → Enviar alerta al administrador: "CIRCUIT BREAKER ACTIVADO: Flujo [nombre] desactivado tras 3 fallos consecutivos. Última vez: [hora]. Error: [descripción]. Acción requerida antes de reactivar." → Activar procedimiento manual de respaldo si existe CONDICIÓN DE REACTIVACIÓN (manual): → Administrador investiga la causa del fallo → Corrige el problema → Resetea contador_fallos a 0 → Reactiva manualmente el escenario en Make EJEMPLO CLÍNICO: Flujo de alertas de valores críticos del laboratorio → Si el webhook del HIS empieza a enviar datos malformados y el flujo falla 3 veces seguidas, el circuit breaker desactiva el flujo automatizado e inmediatamente notifica al equipo para activar el protocolo manual de notificación de valores críticos — evitando que sigan fallando sin que nadie lo sepa mientras los valores críticos no se comunican
Monitorización del ecosistema de automatizaciones
No puedes gestionar lo que no monitorizas. Un ecosistema de 20 flujos activos necesita un sistema de monitorización que detecte fallos antes de que generen impacto clínico o que los detecte en el momento en que ocurren para activar los procedimientos de respaldo.

🔴
Alerta crítica: fallo en flujo de impacto clínico directo
Para flujos con impacto clínico (alertas de valores críticos, seguimiento de crónicos): SMS inmediato + llamada al administrador del ecosistema. Incluir: nombre del flujo, error detectado, última ejecución exitosa, y enlace directo a Make/n8n para acceso rápido. Tiempo de respuesta objetivo: <15 minutos.
🟡
Alerta media: degradación de rendimiento
Para flujos que no fallan completamente pero tardan más de lo normal (ej: el flujo de recordatorios tarda 45 min en lugar de los 10 habituales): email al administrador en el mismo día. Puede indicar sobrecarga de una API externa, degradación del HIS, o aumento del volumen de datos que requiere optimización.
📊
Informe semanal de salud del ecosistema
Cada lunes: email automático con el resumen de la semana. Número de ejecuciones totales, tasa de éxito, flujos con mayor número de fallos, tendencia de rendimiento, cambios realizados en la semana, y próximo mantenimiento planificado. Este informe es la base para la reunión mensual de revisión del ecosistema.

Mantenimiento y mejora continua del ecosistema
Un ecosistema de automatizaciones no es un proyecto que se termina — es una infraestructura que se mantiene y evoluciona. Las APIs cambian, el HIS se actualiza, los procesos clínicos se modifican, aparecen nuevas necesidades. El mantenimiento planificado es la diferencia entre un ecosistema que crece ordenadamente y uno que colapsa por acumulación de deuda técnica.
CALENDARIO DE MANTENIMIENTO DEL ECOSISTEMA: DIARIO (automatizado): → Revisión del dashboard de salud (primer acceso del administrador: 8:00 AM) → Verificar que los flujos críticos ejecutaron correctamente durante la noche → Revisar alertas pendientes de resolución SEMANAL (manual + automatizado): → Informe semanal de salud generado automáticamente → Revisión de flujos con rendimiento degradado → Limpieza de logs de ejecución de flujos no críticos MENSUAL (manual): → Revisión del inventario de flujos: ¿alguno ha quedado obsoleto? → Verificar que las credenciales de APIs no han expirado → Revisar los límites de uso de las plataformas (operaciones Make, SMS Twilio) → Comprobar que las DPAs con proveedores están vigentes → Actualizar la documentación de los flujos modificados TRIMESTRAL: → Auditoría completa del ecosistema con el prompt de auditoría → Revisión de KPIs de los flujos: ¿están generando el valor esperado? → Planificación de nuevas automatizaciones para el siguiente trimestre ANUAL: → Renovación de contratos con proveedores (Make, Zapier, Twilio) → Evaluación de si la plataforma actual sigue siendo la más adecuada → Revisión completa de cumplimiento RGPD y ENS
🔄
Gestión de cambios en el HIS o en los procesos
Cuando el HIS se actualiza, puede cambiar el formato de los datos que exporta, la estructura de la API, o los campos disponibles. Antes de cualquier actualización del HIS, el responsable del ecosistema debe revisar qué flujos usan ese sistema y probarlos en el entorno de pruebas con los nuevos datos.
📋
Control de versiones de los flujos
Make y n8n tienen historial de versiones de los escenarios/workflows. Antes de modificar un flujo en producción, crear una copia de seguridad con la versión actual. Si el cambio genera problemas, el rollback a la versión anterior es cuestión de minutos.
🧪
Entorno de pruebas del ecosistema
Mantener una instancia separada (o escenarios de «prueba» en Make) donde se prueban los cambios antes de desplegarlos a producción. Especialmente importante para cambios en flujos críticos: nunca modificar directamente el flujo de alertas de valores críticos en producción sin haberlo probado en el entorno de pruebas primero.
Prompt: optimizar un flujo que ha empezado a fallar o a funcionar lento
Tengo un flujo de automatización en [Make/n8n] que empezó a funcionar correctamente pero en las últimas semanas está generando errores frecuentes o tarda mucho más de lo normal. SÍNTOMAS: - Flujo: [nombre y descripción breve] - Problema observado: [fallos / lentitud / datos incorrectos] - Frecuencia del problema: [cuántas ejecuciones de cada X fallan] - Últimos cambios realizados (en el flujo o en los sistemas que usa): [descripción] - Mensaje de error más frecuente (si aplica): [pegar el error] - Tendencia: [empeoró de golpe / empeoró gradualmente] Ayúdame a diagnosticar: 1. Las causas más probables del problema según los síntomas descritos 2. Cómo verificar cada hipótesis (qué revisar, en qué orden) 3. Soluciones para cada causa probable 4. Cómo prevenir que el problema se repita 5. Si el problema es un límite de la plataforma actual, alternativas para escalar o migrar
El diagnóstico de un flujo que falla sin saber por qué puede tomar horas si no hay metodología. Este prompt aplica un proceso de diagnóstico estructurado — de lo más probable a lo menos probable — ahorrando tiempo y evitando los cambios «a ciegas» que pueden generar problemas nuevos.
Pregunta 1 de 3
El flujo de alertas de valores críticos de laboratorio ha fallado 3 veces consecutivas porque el HIS ha cambiado el formato del webhook que envía. El circuit breaker se activa y desconecta el flujo. ¿Cuál es la secuencia correcta de acciones?
Pregunta 2 de 3
Dos flujos (el de recordatorios y el de gestión de lista de espera) escriben simultáneamente en la misma hoja de Google Sheets. Esta mañana los datos aparecen incorrectos. ¿Cuál es la solución arquitectónica correcta?
Pregunta 3 de 3
El responsable del ecosistema detecta en el informe mensual que el flujo de reporting semanal de calidad ha tardado un promedio de 47 minutos en las últimas 4 semanas, cuando antes tardaba 8 minutos. No hay errores, solo lentitud. ¿Cuál es la causa más probable y cómo verificarla?
