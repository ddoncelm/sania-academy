Integración con HIS: APIs, webhooks
y estándares HL7 FHIR para conectar automatizaciones con el núcleo hospitalario
15-20 minutos
Nivel intermedio-avanzado
Interoperabilidad
0%
Objetivo de la lección
Entender cómo conectar flujos de automatización con el Sistema de Información Hospitalario (HIS) — el núcleo de datos clínicos del hospital — utilizando las alternativas técnicas disponibles según el grado de apertura de cada sistema: API REST nativa, HL7 FHIR, webhooks, o estrategias sin API cuando el HIS no las ofrece.
🔌 Analogía clínica
El HIS es como el sistema circulatorio del hospital: todos los datos fluyen por él. Las automatizaciones que creamos en lecciones anteriores son como órganos periféricos — son útiles, pero solo se vuelven plenamente funcionales cuando tienen conexión sanguínea con el sistema central. Sin integración con el HIS, las automatizaciones trabajan con datos sacados a mano del sistema (como extraer sangre por punción para cada análisis). Con integración, los datos fluyen automáticamente.
🏥
¿Qué es el HIS?
Sistema de Información Hospitalario: el software central que gestiona la historia clínica electrónica, citaciones, admisión/alta, prescripción, y resultados de pruebas. En España: SAP IS-H, Selene, Millennium (Cerner), Medora, Horos, y sistemas propios autonómicos.
🔗
¿Por qué integrar?
Sin integración: exportas datos manualmente del HIS → los subes a tu automatización. Con integración: los datos fluyen automáticamente en tiempo real. La diferencia entre un flujo que depende de una persona y uno que funciona solo.
📋
Alternativas técnicas
De más a menos deseable: API REST nativa del HIS → FHIR endpoint → webhook del HIS → polling de base de datos (con permisos) → exportación CSV automatizada → lectura de email/notificación del HIS.
⚠️
Realidad del SNS
Muchos HIS de hospitales públicos españoles tienen APIs limitadas o sin documentar. El TIC del hospital y el proveedor del HIS son interlocutores clave. No siempre la opción óptima es técnicamente viable — hay que trabajar con lo disponible.
HL7 FHIR: el estándar de interoperabilidad sanitaria
HL7 FHIR (Fast Healthcare Interoperability Resources) es el estándar internacional de interoperabilidad para sistemas de información sanitaria. Los HIS modernos que implementan FHIR exponen sus datos a través de una API REST estandarizada que cualquier sistema puede consumir.
FHIR explicado sin tecnicismos
Imagina que cada elemento de la historia clínica (paciente, diagnóstico, medicación, resultado de prueba, cita) es un «recurso» con un formato estándar definido internacionalmente. FHIR define la estructura de cada recurso y cómo pedirlo al sistema. Si el HIS implementa FHIR, puedes pedirle «dame todas las citas de mañana del servicio de cardiología» y recibirás la respuesta en un formato siempre igual, independientemente del HIS específico.
✅
Ventaja clave: independencia del HIS específico
Una automatización construida sobre FHIR funciona con cualquier HIS que implemente el estándar — Cerner, Epic, SAP IS-H, o cualquier otro. No depende de las particularidades técnicas de cada proveedor.
📍
Adopción en España
El SNS está impulsando FHIR a través de la Estrategia de Salud Digital. SAP IS-H (usado en varios hospitales de Andalucía, Madrid y otras CCAA) tiene módulo FHIR. Cerner Millennium incluye FHIR nativo. Selene (usado en Osakidetza y otros) tiene desarrollo progresivo de FHIR. La adopción varía según el hospital y la versión del HIS.
🔐
Autenticación y autorización
Los endpoints FHIR requieren autenticación SMART on FHIR (basada en OAuth 2.0). El acceso debe estar autorizado por el TIC del hospital para cada aplicación que quiera consumir datos del HIS. Ninguna automatización debe acceder al HIS sin este proceso de autorización formal.
RECURSOS FHIR MÁS RELEVANTES PARA AUTOMATIZACIÓN: Patient — Datos del paciente → Campos útiles: id, nombre, birthDate, telecom (teléfono), address Appointment — Cita → Campos útiles: start, end, status, serviceType, participant → Status values: proposed | pending | booked | arrived | fulfilled | cancelled Encounter — Episodio asistencial (ingreso, consulta, urgencia) → Campos útiles: status, class, type, period (start/end), hospitalization Observation — Resultado clínico (analítica, constante, exploración) → Campos útiles: code (LOINC), value, interpretation (H/L/N/A=alta/baja/normal/alarma) → Para valores críticos: interpretation = "AA" (alert-above) o "LL" (alert-below) MedicationRequest — Prescripción → Campos útiles: medication, dosageInstruction, status, authoredOn DiagnosticReport — Informe diagnóstico (radiólogo, anatomopatólogo) → Campos útiles: status, code, conclusion, presentedForm (PDF del informe) Condition — Diagnóstico → Campos útiles: code (ICD-10), clinicalStatus, verificationStatus, onsetDateTime
CONSULTAS FHIR PRÁCTICAS: BASE URL EJEMPLO: https://his.hospital.es/fhir/R4/ 1. Obtener citas de mañana del Servicio de Cardiología: GET /Appointment?date=2025-01-15&service-type=394579002&status=booked 2. Obtener observaciones con interpretación crítica en las últimas 6 horas: GET /Observation?date=gt2025-01-14T18:00:00&interpretation=AA,LL 3. Obtener ingresos activos del servicio de Medicina Interna: GET /Encounter?status=in-progress&service-type=394814009 4. Buscar paciente por nombre y fecha de nacimiento: GET /Patient?name=Garcia&birthdate=1965-03-15 5. Obtener prescripciones activas de un paciente: GET /MedicationRequest?subject=Patient/12345&status=active EN MAKE (módulo HTTP Request): → URL: base_url + endpoint FHIR → Headers: Authorization: Bearer [token_oauth] → Headers: Accept: application/fhir+json → Method: GET → Resultado: JSON con la lista de recursos

APIs REST propietarias del HIS
Muchos HIS, especialmente los más antiguos o los desarrollados internamente por las CCAA, tienen APIs REST propietarias — no estándar FHIR pero funcionalmente equivalentes para casos de uso específicos. El proceso de trabajo es similar pero la documentación de la API varía entre sistemas.
1️⃣
Paso 1: Identificar si el HIS tiene API documentada
Contactar con el TIC del hospital. Preguntar: «¿Tiene el HIS una API REST documentada para integraciones externas?» Si sí, pedir la documentación (Swagger/OpenAPI es el formato estándar). Si no, pasar a la sección de estrategias sin API.
2️⃣
Paso 2: Proceso de autorización formal
Ningún acceso a la API del HIS debe hacerse sin un proceso formal de autorización del responsable de TI y del responsable de protección de datos. Requiere: descripción del flujo, datos a los que accede, sistemas que recibirán los datos, medidas de seguridad implementadas. Puede tomar semanas — planificalo.
3️⃣
Paso 3: Entorno de pruebas (sandbox)
Nunca desarrolles y pruebes directamente contra la base de datos de producción del HIS. El HIS debe tener un entorno de pruebas (sandbox) con datos sintéticos o anonimizados donde desarrollar y validar la integración antes de pasar a producción.
4️⃣
Paso 4: Implementación con rate limiting
Las APIs del HIS tienen límites de peticiones (rate limiting) para proteger el rendimiento del sistema. Configura tu flujo para no superar estos límites: añade delays entre peticiones, usa cache cuando sea posible, y evita polling excesivamente frecuente en horarios de alta carga asistencial.
Tipos de autenticación en APIs de HIS
🔑
API Key (la más simple)
Una clave estática que se incluye en el header de cada petición. Simple de configurar en Make (variable de entorno). Debe rotarse periódicamente y nunca incluirse en el código visible. En Make: Header → «X-API-Key: tu_clave».
🔒
OAuth 2.0 / JWT (el más seguro)
El flujo obtiene primero un token de acceso temporal (válido 1-24h) usando credenciales seguras, y usa ese token para las peticiones a la API. Make tiene módulo nativo para OAuth 2.0. Es el estándar SMART on FHIR. Requiere configurar el endpoint de token del HIS.
🔐
Certificado cliente (el más común en SNS)
El sistema que llama a la API debe tener instalado un certificado digital que el HIS reconoce. Muy usado en integraciones en la red SARA del SNS. Requiere que TIC genere y gestione el certificado. En Make no es nativamente soportado — requiere un middleware o n8n self-hosted.
Webhooks del HIS: el HIS nos llama a nosotros
En lugar de que la automatización pregunte periódicamente al HIS («polling»), el HIS puede notificar a la automatización cuando ocurre un evento relevante. Esto se llama webhook o push notification. Es más eficiente y permite reacción en tiempo real.
CONFIGURACIÓN DE WEBHOOK DEL HIS EN MAKE: 1. Make genera una URL única de webhook para tu escenario: Ejemplo: https://hook.eu1.make.com/abcdefg123456789 2. El TIC del hospital configura el HIS para enviar un HTTP POST a esa URL cuando ocurra el evento definido: - Alta de paciente - Nuevo ingreso - Resultado crítico de laboratorio - Cita cancelada - Cambio de estado de episodio 3. El cuerpo del POST contiene los datos del evento en JSON: { "event": "patient_discharged", "timestamp": "2025-01-15T14:32:00Z", "patient_id": "123456", "ward": "cardiologia", "discharge_type": "home" } 4. Make procesa el JSON y desencadena las acciones del flujo VENTAJA SOBRE POLLING: → Polling cada 15 min = demora máxima 15 min en reaccionar al evento → Webhook = demora máxima 2-5 segundos en reaccionar al evento
Estrategias de integración cuando el HIS no tiene API
La realidad de muchos hospitales del SNS: el HIS es un sistema legado sin API documentada, sin FHIR, sin webhooks. Esto no impide la automatización — requiere estrategias alternativas.
Exportación CSV programada — La más común en el SNS
La mayoría de HIS permiten configurar exportaciones automáticas a CSV/Excel en una ubicación de red compartida o carpeta local. Esta exportación programada (diaria, por turno, o en tiempo real según el HIS) es la base de muchas automatizaciones en hospitales sin API.
FLUJO: Automatización basada en exportación CSV del HIS CONFIGURACIÓN EN EL HIS: → Solicitar al TIC que configure una exportación programada de: - Altas del día a las 22:00 → CSV en carpeta \\servidor\exports\altas\ - Citas de mañana a las 23:00 → CSV en carpeta \\servidor\exports\citas\ → Formato requerido: CSV UTF-8, con encabezado en primera fila → Campos mínimos necesarios para tu flujo: [definir con TIC] EN MAKE (o n8n): → Trigger: Schedule a las 23:15 (después de que el HIS haya exportado) → Módulo: "Read a File from a Folder" (Microsoft SharePoint o Google Drive) O: HTTP Request GET a URL interna del CSV (si está en servidor web) → Módulo: "Parse CSV" → transforma cada fila en un objeto JSON → Iterator: procesar cada registro → [Acciones del flujo para cada registro] LIMITACIÓN CLAVE: La exportación CSV implica latencia (mínimo horas) — no es tiempo real. Para procesos donde las horas no importan (recordatorios del día siguiente, reporting diario, cartas de alta), es perfectamente válido.
Email de notificación del HIS como trigger
Muchos HIS envían emails automáticos al personal cuando ocurren ciertos eventos: nuevo resultado de laboratorio disponible, alta registrada, cita cancelada. Estos emails pueden usarse como trigger de automatización.
FLUJO: Trigger por email del HIS en Make CONFIGURACIÓN: → Crear un email dedicado solo para recibir notificaciones del HIS: ejempl: notificaciones-his@hospital.es (bandeja Gmail/Outlook) → Make: módulo "Watch Emails" (Gmail o Outlook connector) → Trigger: nuevo email en la bandeja → Filtro: De = "noreply@his.hospital.es" Y Asunto contiene = "Alta registrada" → Módulo "Parse Email" o expresión regular para extraer los datos del email: - Número de historia clínica (patrón: HCL-[0-9]+) - Nombre del paciente - Servicio - Timestamp del alta → Acciones del flujo con los datos extraídos LIMITACIÓN: Extraer datos de texto de email es frágil si el formato del email del HIS cambia. Configurar el HIS para que el email incluya los datos en formato estructurado (JSON en el cuerpo, o como adjunto CSV) es mucho más robusto.
Acceso directo a la base de datos del HIS (solo lectura)
En algunos hospitales, el TIC puede conceder acceso de solo lectura a la base de datos del HIS (SQL Server, Oracle, PostgreSQL) a través de una conexión segura. Esto permite queries directas sin depender de que el HIS tenga API.
⚠️ Requiere autorización formal y coordinación con TIC
El acceso directo a la base de datos del HIS es la opción más potente pero también la más sensible. Requiere: autorización formal del responsable de TI y del DPD, vistas de solo lectura creadas por el DBA (nunca acceso a tablas completas), usuario de base de datos con permisos mínimos, conexión a través de VPN o red interna, y auditoría de accesos activada.
EN n8n self-hosted (dentro de la red del hospital): → Nodo "MySQL" / "PostgreSQL" / "SQL Server" → Credenciales: servidor, base de datos, usuario de solo lectura, contraseña → Query de ejemplo (vista creada por el DBA, no tabla real): SELECT Servicio, COUNT(*) as Total_Altas, AVG(Estancia) as Estancia_Media FROM v_altas_hoy -- vista creada por DBA, datos ya agregados WHERE fecha_alta = CURDATE() GROUP BY Servicio NOTA: n8n self-hosted dentro de la red del hospital es la única plataforma de automatización que puede acceder directamente a la BD del HIS sin que los datos salgan de la infraestructura hospitalaria.
