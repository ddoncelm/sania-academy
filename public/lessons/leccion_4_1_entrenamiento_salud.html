Objetivo de la lección
Entender las tres grandes estrategias para adaptar modelos de IA a contextos clínicos específicos — prompt engineering avanzado, fine-tuning y RAG (Retrieval-Augmented Generation) — y saber elegir la correcta para cada necesidad sin necesidad de conocimientos de programación profundos.
🎓 Analogía clínica
Adaptar un modelo de IA a tu especialidad es como formar a un médico de nueva incorporación al servicio. El prompt engineering es darle el briefing de guardia: «en este servicio hacemos las cosas así, el protocolo es este». El RAG es darle acceso a la biblioteca del servicio: «si tienes dudas, consulta estas guías». El fine-tuning es el equivalente a la residencia completa en la especialidad: el médico interioriza profundamente el conocimiento hasta que responde como un especialista, no como un médico de guardia con briefing. Cada estrategia tiene su momento y su coste.
📝
Prompt Engineering
Instruir al modelo en el momento de la consulta. Sin datos de entrenamiento. Resultado inmediato. La más rápida y barata. Limitada por el contexto de la ventana.
📚
RAG (Retrieval-Augmented Generation)
El modelo consulta una base de conocimiento externa antes de responder. Escalable. Siempre actualizable. Sin cambiar el modelo. Ideal para protocolos y evidencia.
🧠
Fine-tuning
Reentrenar el modelo con datos propios del dominio. Cambia los pesos del modelo. El resultado más especializado pero también el más costoso y el más difícil de actualizar.
Por qué esto importa en sanidad
Un modelo de IA generalista sabe de medicina, pero no sabe cómo funciona tu servicio, qué protocolos usa tu hospital, o cuál es la terminología que usáis internamente. Las tres estrategias permiten cerrar esa brecha — a costes y complejidades muy distintos. Elegir mal puede significar gastar meses en un fine-tuning cuando bastaba un RAG con los protocolos del hospital.
Fine-tuning: cuándo es realmente necesario
El fine-tuning es la estrategia más sobreestimada en el ecosistema de IA clínica. Muchos proyectos que se anuncian como «modelo entrenado con datos de nuestro hospital» obtienen resultados equivalentes o peores que un buen RAG con el mismo coste veinte veces mayor. Aquí está la guía honesta de cuándo es la opción correcta.
✅
Cuándo el fine-tuning es la respuesta correcta
Cuando el modelo necesita cambiar su formato de respuesta de forma consistente (ej: siempre responder en formato SOAP, siempre en castellano clínico, siempre con un nivel de tecnicismo específico). Cuando el dominio es tan especializado que el modelo base comete errores frecuentes incluso con prompts elaborados. Cuando el volumen de uso es muy alto y el coste de incluir contexto extenso en cada prompt se vuelve inasumible. Cuando necesitas que el modelo funcione sin conexión a internet o con datos que nunca deben salir al cloud.
❌
Cuándo NO usar fine-tuning
Para actualizar el conocimiento del modelo con documentos recientes (protocolos nuevos, guías publicadas este año): usa RAG. Para que el modelo recuerde información de conversaciones anteriores: usa memoria o context management. Para que el modelo «sepa» el protocolo de tu UCI: prueba primero con RAG. Para resolver un problema de alucinaciones: el fine-tuning no las elimina — puede empeorarlas si los datos de entrenamiento son insuficientes.
⚠️ El error más común en proyectos de IA clínica
Equipos que invierten 6 meses preparando datos de entrenamiento y 50.000€ en fine-tuning para obtener un modelo que responde peor que Claude o GPT-4 con un buen prompt del sistema. Antes de iniciar cualquier proyecto de fine-tuning, demuestra que ni prompt engineering ni RAG resuelven el problema. La carga de la prueba está en justificar el fine-tuning, no al revés.
El proceso de fine-tuning simplificado
PROCESO DE FINE-TUNING (sin programación): PASO 1 — DEFINIR EL CASO DE USO CONCRETO: No: «mejorar el modelo para nuestro hospital» Sí: «que el modelo genere siempre informes de alta en formato HUCS con las secciones en el orden estándar de nuestro servicio» PASO 2 — PREPARAR EL DATASET: Formato requerido por OpenAI/Anthropic/Ollama: JSONL Cada línea es un ejemplo: {«prompt»: «input», «completion»: «output ideal»} Cantidad mínima: 50-100 ejemplos para resultados básicos 500-1000 ejemplos para resultados robustos Calidad > Cantidad: 100 ejemplos de alta calidad > 1000 ejemplos mediocres PASO 3 — LIMPIEZA Y CURACIÓN: Eliminar ejemplos con errores clínicos o de formato Verificar que el dataset es representativo de todos los casos Anonimizar / pseudonimizar (NUNCA usar datos reales de pacientes sin anonimización completa previamente verificada) PASO 4 — ENTRENAMIENTO (en plataforma): OpenAI Fine-tuning API: sube el JSONL, elige el modelo base (gpt-4o-mini es la opción más coste-eficiente), lanza el job, espera 30-120 min Google Vertex AI: para modelos Gemini Hugging Face AutoTrain: para modelos open source (Llama, Mistral) PASO 5 — EVALUACIÓN: Comparar el modelo fine-tuneado vs. modelo base con el mismo prompt en al menos 50 casos de prueba no vistos durante el entrenamiento Si no hay mejora significativa en esos 50 casos: el problema no era fine-tuning — volver a step 1
🔐
Datos de entrenamiento: las reglas absolutas en sanidad
NUNCA usar datos de pacientes identificables para entrenamiento sin anonimización completa verificada y sin aprobación del Comité de Ética e Investigación (CEI). La anonimización debe cumplir el estándar del test de Mosaic (imposibilidad de reidentificación por combinación de campos). Las notas clínicas, informes de alta y resultados de pruebas solo pueden usarse como datos de entrenamiento si están completamente anonimizados.
📋
Consentimiento y base legal
El RGPD exige una base legal para el tratamiento de datos con fines de entrenamiento de IA. En la práctica hospitalaria, la base más robusta es el interés público o el consentimiento explícito para investigación. Antes de cualquier proyecto de fine-tuning con datos clínicos, consultar con el DPD del hospital y el CEI. El proceso puede tomar 3-6 meses.
☁️
¿Dónde entrenar? Cloud vs. local
Para datos que no pueden salir del hospital (incluso anonimizados): entrenamiento local con Ollama + modelos open source (Llama 3, Mistral) en servidores propios. Para datos anonimizados con garantías: plataformas cloud con DPA y servidores UE (OpenAI Enterprise, Azure OpenAI). La elección afecta al presupuesto, al tiempo y al nivel de control.
RAG médico: la estrategia más potente para sanidad
RAG (Retrieval-Augmented Generation) permite que el modelo consulte una base de conocimiento externa — protocolos del hospital, guías clínicas, evidencia científica — en el momento en que el usuario hace la pregunta, sin necesidad de reentrenar el modelo. Es la estrategia más versátil y mantenible para entornos sanitarios.
ARQUITECTURA RAG — PASO A PASO: 1. INDEXACIÓN (se hace una vez, se actualiza cuando hay cambios): → Los documentos (protocolos, guías, evidencia) se dividen en fragmentos (chunks) → Cada chunk se convierte en un vector numérico (embedding) que captura su significado → Los vectores se guardan en una base de datos vectorial (Pinecone, Weaviate, Chroma, pgvector en Supabase) 2. EN CADA CONSULTA: → El usuario hace una pregunta: «¿cuál es la dosis de vancomicina en IR grave?» → La pregunta se convierte en vector → La base vectorial busca los chunks más similares semánticamente → Los 3-5 chunks más relevantes se incluyen en el contexto del prompt → El modelo responde basándose en esos chunks + su conocimiento base → La respuesta incluye las fuentes (qué protocolo, qué sección) 3. VENTAJAS SOBRE FINE-TUNING: → Actualizable: cuando cambia un protocolo, se re-indexa ese documento → Trazable: el modelo cita las fuentes que usó para responder → Auditorio: puedes ver exactamente qué documentos influyeron en la respuesta → Más barato: no requiere reentrenamiento, solo mantenimiento de la base
📋
Protocolos y procedimientos del hospital
Los protocolos del servicio en PDF o Word son la fuente más valiosa para RAG clínico. El modelo puede responder preguntas de guardia («¿cuándo se activa el protocolo de sepsis?») citando exactamente el protocolo en vigor. Ventaja clave: los protocolos se actualizan sin reentrenar el modelo.
📖
Guías clínicas de sociedades científicas (ESC, AHA, SEPAR…)
Las guías en PDF pueden indexarse directamente. El modelo puede responder preguntas sobre recomendaciones con el grado de evidencia correcto, citando la sección exacta de la guía. Requiere una estrategia de actualización: cuando la sociedad publica una guía nueva, se re-indexa.
🔬
PubMed abstracts (visto en lección 3.6)
El sistema de vigilancia bibliográfica del módulo 3 puede alimentar automáticamente la base vectorial con los abstracts de los artículos más relevantes. El modelo responde preguntas clínicas con evidencia publicada en los últimos 90 días — algo imposible con un modelo base con fecha de corte.
💊
Vademécum / ficha técnica de medicamentos
La AEMPS publica las fichas técnicas de todos los medicamentos aprobados en España. Indexarlas permite que el modelo responda preguntas de dosis, contraindicaciones e interacciones con las fichas oficiales actualizadas como fuente, no solo con su conocimiento de entrenamiento.
Prompt: diseñar el sistema RAG para el servicio
Necesito diseñar un sistema RAG (Retrieval-Augmented Generation) para el Servicio de [ESPECIALIDAD]. El objetivo es que el personal del servicio pueda hacer preguntas en lenguaje natural sobre: [LISTA DE CASOS DE USO: consultas de protocolo, dosis de medicamentos, criterios de ingreso, etc.] Documentos disponibles para indexar: [LISTA: protocolos PDF, guías clínicas, vademécum local, SPC de medicamentos] Proporciona: 1. Arquitectura recomendada: qué base vectorial usar según el presupuesto y la privacidad requerida (Supabase pgvector si datos pueden estar en cloud con DPA / Chroma local si no pueden salir) 2. Estrategia de chunking: cómo dividir los documentos para que los fragmentos sean coherentes (capítulo por capítulo, página por página, por sección marcada con H2, etc.) 3. Proceso de indexación: paso a paso para subir los primeros 10 documentos 4. Prompt del sistema para el asistente RAG (cómo debe comportarse, cómo citar fuentes, qué hacer cuando no encuentra la respuesta en los documentos) 5. Interfaz de usuario: cómo hacer accesible el sistema al personal sin conocimientos técnicos 6. Política de actualización: con qué frecuencia re-indexar y cómo detectar que un documento está desactualizado en la base vectorial
El éxito de un sistema RAG en sanidad depende más del diseño de la base de conocimiento que de la tecnología. Un buen chunking con documentos bien seleccionados supera a una tecnología sofisticada con documentos mal estructurados. Este prompt produce el diseño completo antes de tocar ninguna tecnología.

Prompt: elegir la estrategia correcta para un caso concreto
Quiero adaptar un modelo de IA para el siguiente caso de uso en el Servicio de [ESPECIALIDAD]: NECESIDAD CONCRETA: [Descripción detallada: qué pregunta debe responder el modelo, qué formato debe tener la respuesta, con qué frecuencia se consultará, quién lo consultará] CONTEXTO: - Disponemos de: [documentos propios / datos de casos anteriores / solo conocimiento general del dominio] - Presupuesto: [bajo / medio / alto] - Plazo: [urgente (<2 semanas) / medio plazo / largo plazo] - Requisitos de privacidad: [datos deben quedar en el hospital / pueden ir a cloud UE / sin restricciones] - Perfil técnico del equipo: [ninguno / básico / avanzado] Analiza la necesidad y recomienda: 1. La estrategia óptima (prompt engineering / RAG / fine-tuning / combinación) 2. Por qué las otras estrategias no son la mejor opción para este caso 3. Los primeros 3 pasos concretos para implementar la estrategia recomendada 4. Cómo medir si la implementación está siendo exitosa (métricas de evaluación) 5. Si recomiendas RAG: qué documentos indexar primero y cómo estructurar el prompt del sistema
La elección de estrategia es la decisión más importante — equivocarse supone meses de trabajo perdido. Este prompt fuerza un análisis multidimensional antes de comprometerse con una dirección técnica. Úsalo en la fase de diseño, no después de empezar a construir.
Pregunta 1 de 3
El jefe del Servicio de Urgencias quiere que el modelo de IA responda siempre preguntas sobre los criterios de activación de los códigos del hospital (código sepsis, código ictus, código trauma) citando el protocolo vigente en ese hospital. El protocolo se actualiza cada 6-12 meses. ¿Qué estrategia es la más adecuada?
Pregunta 2 de 3
Un hospital quiere usar datos de informes de alta de los últimos 5 años (con nombre del paciente, diagnóstico, evolución clínica y médico firmante) para entrenar un modelo de IA. ¿Qué condición es absolutamente imprescindible antes de poder usar esos datos?
Pregunta 3 de 3
Un servicio ha implementado RAG con los protocolos del hospital y observa que el modelo a veces «alucina» información no presente en los protocolos indexados. ¿Cuál es la causa más probable y la solución?
